## Frontend Environment Variables (Vercel)

**Location**: Vercel Dashboard → Project Settings → Environment Variables

**Important**: Frontend variables MUST have `NEXT_PUBLIC_` prefix to be embedded in client bundle.

### Required Variables

| Variable | Example Value | Source | Used By |
|----------|---------------|--------|---------|
| `NEXT_PUBLIC_API_URL` | `https://api.socialpro.railway.app/api/v1` | Manually set | Frontend API client (`apps/web/src/lib/api-client.ts`) |
| `NEXT_PUBLIC_APP_URL` | `https://socialpro.vercel.app` | Manually set | Frontend links, redirects, callback URLs |
| `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` | `pk_live_...` | From Stripe dashboard | Stripe payment modal in billing page |

### Where to Find Values

1. **`NEXT_PUBLIC_API_URL`**
   - After deploying backend on Railway
   - Format: `https://[railway-domain]/api/v1`
   - Example: `https://api.socialpro.railway.app/api/v1`

2. **`NEXT_PUBLIC_APP_URL`**
   - Your Vercel project URL
   - Shown in Vercel dashboard after first deployment
   - Example: `https://socialpro.vercel.app`
   - Can also use custom domain if configured

3. **`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`**
   - Stripe Dashboard → Developers → API keys
   - Use **LIVE** key in production (starts with `pk_live_`)
   - Use **TEST** key for development (starts with `pk_test_`)

### Setting in Vercel

**Via Dashboard:**
1. Vercel Dashboard → Project → Settings → Environment Variables
2. Click "Add New"
3. Name: `NEXT_PUBLIC_API_URL`
4. Value: `https://api.socialpro.railway.app/api/v1`
5. Select environments: **Production**, **Preview**, **Development**
6. Save
7. Trigger rebuild/redeploy

**Via CLI:**
```bash
vercel env add NEXT_PUBLIC_API_URL
# Follow prompts
vercel redeploy  # Trigger new deployment with new vars
```

## Backend Environment Variables (Railway)

**Location**: Railway Dashboard → Project → Service (API) → Variables

**Important**: Backend variables are NOT prefixed with `NEXT_PUBLIC_` — they're server-side only.

### Core Configuration

| Variable | Example | Notes |
|----------|---------|-------|
| `NODE_ENV` | `production` | Set to `production` for Railway |
| `PORT` | `4000` | Railway uses this to expose your service |
| `API_URL` | `https://api.socialpro.railway.app` | Your Railway API domain (used for links, callbacks) |

### Database & Cache (Auto-Generated by Railway)

| Variable | Source | Notes |
|----------|--------|-------|
| `DATABASE_URL` | PostgreSQL service | Auto-generated, don't edit manually |
| `REDIS_URL` | Redis service | Auto-generated, don't edit manually |

**Check these are set:**
1. Railway Dashboard → [Your API Service]
2. Variables tab → scroll down
3. `DATABASE_URL` and `REDIS_URL` should be present (Railway auto-adds them from service links)

If not present, link the services:
1. Add PostgreSQL service to project
2. Add Redis service to project
3. Link services to API service
4. Variables auto-populate

### Authentication & Tokens

| Variable | Example | Generate |
|----------|---------|----------|
| `JWT_SECRET` | `a7f3k2m9x1w5q8z...` (32+ chars) | `openssl rand -hex 32` |
| `JWT_REFRESH_SECRET` | `j4k9m2p7l1n6x8v...` (32+ chars) | `openssl rand -hex 32` |
| `JWT_EXPIRES_IN` | `15m` | Use for access token expiry |
| `JWT_REFRESH_EXPIRES_IN` | `7d` | Use for refresh token expiry |
| `ENCRYPTION_KEY` | `a1b2c3d4e5f6...` (32-byte hex) | `openssl rand -hex 32` |

**Generating secrets:**
```bash
# JWT secret
openssl rand -hex 32
# Output: a7f3k2m9x1w5q8z0p2m4j6k8l0n2p4r6s8t0v2w4y6z8a0b2c4d6e8f0g2h4

# Copy into Railway variable
```

## Local Development (.env.local)

**Location**: `.env.local` (in repo root or `apps/api/` if using separate envs)

**Note**: `.env.local` is git-ignored, create from `.env.example`

```bash
# Create from template
cp .env.example .env.local

# Edit with your local values
NEXT_PUBLIC_API_URL=http://localhost:4000/api/v1
NEXT_PUBLIC_APP_URL=http://localhost:3000

# Backend (docker compose)
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/social_pro_dev
REDIS_URL=redis://localhost:6379

# ... other vars with local values
```

**Local Services** (via `docker compose`):
- PostgreSQL: `localhost:5432`
- Redis: `localhost:6379`
- MinIO: `localhost:9000`
- MailHog: `localhost:1025`

## Setting Variables in Railway

### Method 1: Dashboard (Recommended)

1. Railway Dashboard → Your Project → [API Service]
2. Click **Variables** tab
3. Click **Add Variable**
4. Name: (e.g., `NEXT_PUBLIC_API_URL`)
5. Value: (e.g., `https://api.socialpro.railway.app/api/v1`)
6. Save
7. Service auto-restarts

### Method 2: Railway CLI

```bash
# Login
railway login

# Link to project
railway link

# Add variable
railway variable add VARIABLE_NAME value

# Or edit in default editor
railway variable edit
```

## Verifying Variables Are Set

### Frontend (Vercel)

Check that `NEXT_PUBLIC_*` variables are embedded:

1. Deploy to Vercel
2. Open site in browser
3. Open DevTools → Sources → find `_app.js` or similar
4. Search for your URL value (e.g., `api.socialpro.railway.app`)
5. Should be present in bundle (embedded at build time)

### Backend (Railway)

Check that variables are available:

1. Railway Dashboard → [Service] → Logs
2. Look for startup logs showing configuration loaded
3. Or SSH into service:
   ```bash
   railway run env | grep VARIABLE_NAME
   ```

## Common Mistakes

### ❌ Setting `NEXT_PUBLIC_*` vars in Railway only
- They won't be available in frontend!
- Must be in **Vercel Environment Variables**

### ❌ Forgetting to redeploy after setting Vercel env vars
- New variables only take effect on rebuild
- Must redeploy after adding/changing

### ❌ Using localhost URLs in production
- `http://localhost:4000` won't work on Vercel
- Must use deployed backend domain

### ❌ Mixing development and production API keys
- Use test keys locally
- Use live keys in production
- Keep them separate

### ❌ Committing `.env.local` to Git
- Should be git-ignored
- Use `.env.example` as template

## Deployment Order

1. **Deploy backend first** (Railway)
   - Set all backend env vars except `CORS_ORIGIN`
   - Get Railway domain URL

2. **Update backend CORS**
   - Set `CORS_ORIGIN=https://[vercel-domain]` (or placeholder)
   - Deploy again

3. **Deploy frontend** (Vercel)
   - Set `NEXT_PUBLIC_API_URL=https://api.socialpro.railway.app/api/v1`
   - Set `NEXT_PUBLIC_APP_URL=https://[vercel-domain]`
   - Deploy

4. **Test integration**
   - Frontend → Backend calls work
   - CORS not blocking requests
   - Auth flows work end-to-end
